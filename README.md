# 鲜厨记

一个以 HTML、CSS、JavaScript 为核心实现的智能家庭食材存储与烹饪助手。

## 已实现功能

- 食材仓库：添加、编辑、删除、搜索、分类与存储位置筛选
- 图片导入入库：图片预览、文件名演示匹配、名称/分类/存储位置建议与入库前核对
- 新鲜度提醒：根据到期日期自动判断新鲜、临期、当天到期和已过期
- 今日搭配灵感：根据现有库存推荐少量补购即可完成的菜品
- COOK：优先匹配已有菜谱，按库存缩放小份用量；常见肉、蛋、豆腐和蔬菜的新组合可给出本地做法；配置服务端模型后可进一步分析新食材组合。支持按菜名搜索做法，收藏菜谱可跳转查看；牛奶与水果可组合奶昔，选中至少三种水果可组合对应的水果拼盘
- 一周食谱：按周一至周日安排早餐、午餐和晚餐共 21 餐，按餐别推荐并汇总采购食材，勾选已购后可加入仓库
- 烹饪记录：完成时核对实际食材用量，确认后再扣减库存
- 我的菜谱：浏览收藏菜谱、最近生成记录与菜谱详情
- 本地持久化：数据存储于浏览器 localStorage，刷新后不会丢失
- 响应式界面：适配桌面、平板与手机宽度

## 食材视觉素材

`assets/foods/` 中的生菜、豆腐、土豆、洋葱、虾仁、猪排、五花肉、鸡胸肉、排骨和肥牛卷均由用户提供的原图抠出，并加了白色贴纸边。番茄、鸡蛋和牛奶沿用此前生成的图片。图片按食材名称精确映射，未提供图片的食材继续使用带白边的图标。`tools/prepare_food_cutouts.py` 记录了原图裁切和抠图参数；重新处理时需确保原始附件仍在本机临时目录。

第二批用户图片还包括草莓、面包、猕猴桃、樱桃、蓝莓、荔枝、苹果、柠檬、李子、西瓜、桃子、馒头、挂面、大米、胡萝卜、小米、红豆、绿豆、黄豆、花生、蘑菇和玉米。生米图片只对应“大米”；杏鲍菇原图在系统中作为“蘑菇”图片使用，挂面图片同时供菜谱里的“面条”使用。

第三批用户图片包括茄子、黄瓜、西葫芦、苦瓜和长豆角，均从原图抠出并加白边，分别映射到同名蔬菜。

荷兰豆图片同样从用户提供的原图抠出并加白边，单独映射到“荷兰豆”，不会与长豆角混用。

牛肉和鸡腿肉图片分别映射到肉类同名食材；鸡腿肉新增了煎、炖、红烧和蘑菇炒的菜谱，牛肉增加了洋葱炒和青椒炒菜谱。

可乐与鸡翅图片分别映射到饮料和肉类；可乐截图只裁取罐身。可乐示例使用“罐”作为单位，旧版示例中的“瓶”会迁移到“罐”，手动录入的瓶装可乐仍可用于可乐鸡翅的库存匹配。

`assets/dishes/` 收录用户提供的小炒牛肉、清炒荷兰豆、油焖大虾、肉末豆腐和鱼香肉丝菜品照片。每张图保留整只盘子，去除外部背景并加手绘风白边；这些图片用于烹饪结果、周计划和菜谱详情。鱼香肉丝按用户指定的芹菜、黑木耳、五花肉、胡萝卜配料录入。新增的可乐鸡翅、西红柿炒蛋、肉末豆角、酸辣土豆丝、青椒肉丝和清炒西兰花也使用用户提供的整盘照片，以椭圆盘沿抠图并加白边；这些菜和上一批新菜均进入一周食谱候选。

首次打开新版页面时，系统会将图片示例食材补入仓库，并保留已有库存；已有浏览器数据也会执行一次补入。之后手动删除的示例不会因刷新而重新出现。

## 开发流程

1. 需求确认：确定食材仓库、图片识别、临期提醒、AI 烹饪和一周食谱范围。
2. 信息架构：以食材仓库为默认入口，设置四个核心功能页面。
3. 数据建模：建立食材、菜谱、收藏、历史记录和周计划数据结构。
4. 核心开发：实现库存增删改查、筛选、日期计算和 localStorage。
5. 智能逻辑：实现库存匹配、临期优先、今日采购建议与菜谱评分。
6. 视觉设计：采用家庭生活感的米白与绿色配色，完成响应式布局。
7. 验证优化：检查 JavaScript 语法、页面加载、桌面和移动端布局。

## 运行方式

直接双击 `index.html` 即可运行。如果浏览器扩展或本地文件策略影响加载，也可以在当前目录启动静态服务器：

```powershell
python -m http.server 4173
```

然后在浏览器中访问 `http://127.0.0.1:4173/`。

## 图片识别说明

照片导入会在浏览器本地分析白底图片的颜色与外形，给青椒、西红柿、胡萝卜、橙子等提供候选名称；不能可靠判断的图片会留空名称，由用户填写。用户需核对名称、数量、存储位置与到期日期后确认入库。系统会去除连通的白色背景、裁出食材主体，并在透明图外加白色贴纸边；同名食材入库时合并为一条并优先使用新上传的图片；处理后的图片随食材保存在浏览器本地，不需要上传服务器或配置密钥。此方法仅适合清晰的白底单品照片，不能替代通用图像识别模型。未配置模型服务时，烹饪推荐基于本地菜谱库和确定性匹配，水果奶昔与水果拼盘由所选食材在本地组合。文字补充要求支持食材名、忌口、少油、不辣、汤/面等类型、分钟限制及只用现有食材；无法识别的要求会在结果中说明。匹配时至少要用到所选食材；已过期食材不会计入可用库存。菜谱以两人份为基准，结果页会按用餐人数及可用库存调整食材用量，小份会明确标注。

勾选更多食材不会提高最低命中门槛；会优先推荐使用更多所选食材、库存足量且符合时间的菜谱。全部主食材都有库存时，可缩小菜谱份量；例如 1 个鸡翅和 1 罐可乐可制作一份小份可乐鸡翅，记录完成时仅扣减实际建议用量。找不到已有菜谱时，常见的肉、蛋、豆腐和蔬菜搭配会生成有明确步骤的本地建议。缺少某种主食材、过期或超时仍不会当作可以直接完成；菜谱库和本地搭配都无法覆盖时才会显示本地无匹配。

## 接入大模型与密钥安全

项目的前端可以直接上传 GitHub，继续使用本地推荐。不要把个人大模型 API 密钥写在 `app.js`、HTML、前端配置、浏览器 `localStorage` 或 GitHub 仓库中。GitHub Pages 只托管静态页面，无法在页面背后秘密保存并使用密钥。

可选的 `api/recommend.js` 是 Vercel 服务端函数：网页只把已选食材名称、数量和偏好发送到同源接口，函数再使用环境变量 `OPENAI_API_KEY` 调用模型。模型返回的菜谱会在服务端核对食材名称、数量、忌口和时间；不合格或服务不可用时仍显示本地建议。动态菜谱最多保留 40 条在当前浏览器中，供收藏和查看。

启用步骤：将仓库部署到支持 `api/` Node.js 函数的 Vercel 项目；在项目环境变量中设置 `OPENAI_API_KEY`、`COOK_AI_ENABLED=true`，可选设置 `OPENAI_MODEL`（默认 `gpt-5.4-mini`），然后重新部署。`.env.example` 仅列变量名，不能填入真实密钥提交。`.gitignore` 已排除 `.env` 和 `.env.*`，但无法保护已经提交进 Git 历史的密钥。用普通静态服务器或 GitHub Pages 打开页面时，本地推荐照常工作，服务端 AI 接口不可用。

密钥不公开并不等于接口不会被别人调用。此示例在函数中做了每个 IP 每分钟 10 次的简单限制，但无状态云函数实例之间不共享计数。公开部署前还需在平台设置使用额度和可靠的访问控制或持久化限流。只在本人和老师可访问的受保护部署中启用模型接口更合适。食材名称和数量会发给模型服务；图片仍只在浏览器本地处理。

可用 `node tests/cooking-match.test.js` 验证匹配、忌口、时间、别名和份量等场景；用 `node tests/ai-endpoint.test.js` 验证服务端输入输出检查。

```javascript
localStorage.removeItem("foodmind-state-v1");

```
